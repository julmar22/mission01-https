Besoin du client et environnement

La direction veut ouvrir le portail en HTTPS depuis le poste Windows, sans perdre les accès déjà en place.

Contraintes du sujet

  • HTTPS sur le port 443
  • HTTP conservé sur le port 80
  • GLPI sur le port 9999 non modifié
  • Syntaxe vérifiée avant le rechargement
  • Aucun site ni fichier supprimé

Certificat autosigné

Un certificat de laboratoire qui couvre le nom et l’adresse IP du portail. Il chiffre la connexion, mais aucune autorité ne garantit l’identité du serveur.

sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/ssl/private/portail-sio.key \
  -out /etc/ssl/certs/portail-sio.crt \
  -subj "/CN=portail.sio-energie.lan" \
  -addext "subjectAltName=DNS:portail.sio-energie.lan,IP:192.168.20.30"
OptionRôle
req -x509Crée directement un certificat autosigné, sans demande à une autorité
-nodesClé sans mot de passe : Nginx peut démarrer seul, sans intervention
-days 365Validité d’un an
-newkey rsa:2048Génère une nouvelle clé RSA de 2048 bits
-keyout / -outEmplacement de la clé privée et du certificat
-subj "/CN=…"Nom du serveur inscrit dans le certificat
-addext subjectAltNameNoms et IP couverts : les navigateurs ne vérifient que cette liste

Configuration de Nginx en HTTPS

Un nouveau fichier portail-https, séparé de celui du portail HTTP et de celui de GLPI.

server {
    listen 443 ssl;
    server_name portail.sio-energie.lan 192.168.20.30;

    ssl_certificate     /etc/ssl/certs/portail-sio.crt;
    ssl_certificate_key /etc/ssl/private/portail-sio.key;
    ssl_protocols       TLSv1.2 TLSv1.3;

    root /var/www/sio-energie;
    index index.html;
}
LigneRôle
listen 443 sslÉcoute sur le port HTTPS avec TLS
server_nameNoms pour lesquels ce bloc répond
ssl_certificate(_key)Certificat présenté au client et sa clé
ssl_protocolsRefuse les anciennes versions de TLS, trop faibles
root / indexMême dossier que le portail HTTP
  • Activation par un lien dans sites-enabled, sans copier ni supprimer de fichier
  • nginx -t avant chaque rechargement ; reload plutôt que restart : le service n’est pas coupé
  • Port 80 et GLPI non touchés

Test depuis le poste Windows

Le nom est résolu par le fichier hosts du poste, pas par le DNS de srv-ad01. Un enregistrement DNS serait la solution pour tous les postes du domaine.

Un certificat autosigné chiffre la connexion, mais n’établit pas la confiance : Edge affiche « Non sécurisé » parce qu’aucune autorité reconnue ne l’a signé.

Les accès existants fonctionnent toujours

Le sujet demande de montrer le HTTP, GLPI et la persistance après le redémarrage de srv-web. Sous PowerShell, on tape curl.exe : curl seul est un alias d’une autre commande.

Retour arrière, limites et conclusion

Ce qu’il faut savoir pour défaire la modification et ce qu’elle ne règle pas.

Retour arrière

sudo rm /etc/nginx/sites-enabled/portail-https
sudo nginx -t
sudo systemctl reload nginx
  • Seul le lien d’activation est supprimé
  • Retirer la ligne ajoutée au fichier hosts
  • En dernier recours : snapshot MI01-avant-https dans VMware

Limites

  • Certificat autosigné : le navigateur ne lui fait pas confiance
  • En entreprise : autorité de certification interne ou publique
  • Nom résolu par hosts, pas par le DNS Active Directory
  • Port 80 conservé, sans redirection, comme demandé
  • Filtrage entre réseaux prévu au TP5

Conclusion

Le portail est accessible en HTTPS sur le port 443. La configuration est dans un fichier séparé, testée avec nginx -t puis rechargée sans coupure. Le HTTP, GLPI et le routage existants restent en place.
